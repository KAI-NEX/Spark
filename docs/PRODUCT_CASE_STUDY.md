# Spark｜从品牌资料到合作提案的产品案例

更新：2026-09-20。团队项目，AI 辅助实现；当前为本地运行原型。

## 产品问题

品牌合作不只是生成一张联名图。双方首先需要说清各自能提供什么、想获得什么、对消费者有什么价值，以及一份可讨论的提案如何形成。

Spark 将品牌资料、关系探索、合作意向与共创画板连接起来，帮助把模糊想法转成可检查的合作假设。这是当前产品目标，尚未通过真实品牌交易或长期采用验证。

## 关键产品取舍

| 取舍 | 为什么这样做 | 需要承认的限制 |
| --- | --- | --- |
| 用可解释规则探索关系，再用模型理解资料/生成提案 | 把关系依据与表达能力分开，便于检查哪些判断来自什么输入 | 规则权重未经过商业效果校准，分数不是合作成功概率 |
| 复用队友画布与既有运行时 | 让发现流程能进入共创，集中精力解决宿主目标、上下文和交接 | 必须处理数据映射、版本、会话恢复及组件边界；不能将集成写成全部原创 |
| 模板、预载图和本轮 AI 生成分别说明 | 防止一个完整演示被误读成每次都实时生成 | 演示的视觉完整度不能代替生成质量或商业验证 |
| 来源不足时保留探索线索与待确认 | 用户可以探索，但不能把可见节点当成可靠推荐 | 下一步仍需要资料补充与人工判断 |

## 一个具体整合问题

原本机文字适配器只允许一个请求，与共创运行时的双方并行研究冲突。整合记录说明随后支持两条并行、有界排队与取消，并保留版本校验，避免旧结果污染当前会话。

产品意义是使协作步骤的状态和恢复行为可预期，而不是把“更多并发”当成独立卖点。实现和测试细节见 [COLLIDER 接入记录](COLLIDER-INTEGRATION.md)。这是项目执行记录，不能据此认定个人手写了所有实现或已完成真实跨组织协作。

## 当前交付与验证边界

已有品牌发现、资料输入、关系解释、提案/画板接入与状态处理。公开 README 区分确定性规则、模型能力、模板、预载案例和实际生成。部分本地开发内容未必进入当前公开提交，具体发布范围按 Git 版本核对。

真实品牌名称用于非商业演示，不表示授权、合作已经发生或推荐结果有效。没有在此公布真实客户采用、收入或撮合成功率。自动测试检查代码行为，不能代替业务效果验证。

## 下一步：验证一个窄业务任务

先邀请愿意参与的品牌/设计团队，使用已获准使用的 Brief，完成“一份可供内部评审的合作提案”。与现行流程比较：达到可评审稿的耗时、审核轮数、品牌约束错误、实际采用内容和生成/返工成本。

使用者、审核者与付费决策者分别记录。先收集真实需求与验收标准，再运行、观察、修改一个关键问题并复验。试用、采用、付费与真实品牌合作是不同结果，不混写。

本段是拟开展的验证，不是已完成的客户案例。没有真实需求方时，优先完善问题与流程，不为作品集扩展成大型品牌交易平台。
